# Пояснительная записка: локальный запуск Qwen и BGE-M3

**Проект:** `local_ai` · **Дата контрольного запуска:** 1 октября 2026 года.

Эта записка объясняет реализацию из [compose.yaml](../compose.yaml),
[TextTest.py](../TextTest.py) и [EmbeddingsTest.py](../EmbeddingsTest.py).
[test_api.py](../test_api.py) объединяет обе проверки. [Подробные схемы](architecture.md) показывают
те же процессы визуально. Численные результаты взяты из
[отчёта первого запуска](../artifacts/initial-test-report.json);
новые раздельные результаты описаны в разделе 11.

## 1. Что делает система

На одном компьютере запущены два HTTP-сервера с разными моделями.
Первый принимает сообщения и генерирует текстовый ответ. Второй принимает
тексты и вычисляет для них числовые представления — эмбеддинги.

| Задача | Модель | Программа, которая выполняет модель | Результат |
| --- | --- | --- | --- |
| Ответить на вопрос, объяснить тему, составить текст | Qwen2.5-7B-Instruct | llama.cpp, процесс `llama-server` | Текст |
| Представить смысл текста для сравнения и поиска | BGE-M3 | Hugging Face Text Embeddings Inference, сокращённо TEI | Вектор из 1024 чисел |

Например, Qwen получает «Сколько будет 6 × 7?» и отвечает «42». BGE-M3
получает «Кошка спит на диване» и возвращает массив чисел. Сравнивая такой
массив с массивами других текстов, приложение может искать похожие по смыслу
фразы, в том числе на другом языке.

Оба сервера самостоятельны. В текущем проекте Qwen не обращается к BGE-M3,
а BGE-M3 не передаёт результат в Qwen. Их объединяют Docker Compose и
проверочный Python-скрипт. Поиск по пользовательским документам и векторная
база в это задание не входят.

## 2. Основные понятия

| Понятие | Что оно означает в этом проекте |
| --- | --- |
| Модель | Архитектура нейросети и её обученные параметры, позволяющие выполнять определённую задачу |
| Веса | Числовые параметры, полученные при обучении; занимают основную часть скачанных файлов |
| Инференс | Вычисление результата уже обученной моделью по новому входу |
| Движок инференса | Программа, которая читает веса, выполняет вычисления и управляет памятью |
| Токен | Элемент представления текста для модели: слово, часть слова, знак или служебный элемент; токены не равны символам |
| API | Описанный способ обратиться к программе; здесь это HTTP-запросы и JSON-ответы |
| Docker-образ | Пакет с программой сервера и её системными зависимостями |
| Контейнер | Запущенный процесс из образа с собственным окружением и сетевым пространством |
| Docker Compose | Средство, которое по YAML-файлу создаёт контейнеры, сеть, тома и настройки запуска |
| Том, volume | Управляемое Docker хранилище, сохраняющее данные независимо от пересоздания контейнера |
| Эмбеддинг | Вектор, используемый как числовое представление текста для сравнения и поиска |

Здесь выполняется **инференс**. Обучение, дообучение и изменение весов при
обычных запросах не происходят. История диалога, которую клиент передаёт
в `messages`, влияет на текущий ответ, но не переобучает модель.

## 3. Из каких слоёв состоит решение

Пользователь работает в macOS: запускает `python3 test_api.py`, `curl` или
открывает интерфейс llama.cpp. Docker Desktop запускает Linux-окружение,
внутри которого находятся контейнеры `llm` и `tei`. Каждый контейнер
запускает свой сервер и читает свои модельные файлы из подключённого тома.

Для Mac ARM64 выбраны CPU-образы. В этой конфигурации расчёты идут на
процессоре; Metal-ускорение видеоядрами Apple не используется. Это позволяет
выполнить условие задания «в Docker», но влияет на скорость генерации.
Поддерживаемые архитектуры перечислены в
[документации TEI](https://huggingface.co/docs/text-embeddings-inference/en/supported_models)
и [инструкции llama.cpp для Docker](https://github.com/ggml-org/llama.cpp/blob/master/docs/docker.md).

Разделение на два контейнера позволяет независимо перезапускать серверы,
смотреть их логи и менять параметры. При этом ресурсы у них общие:
процессор и память Linux VM Docker Desktop, которая работает на этом Mac.
Выделенные модели потоки и размеры батчей не резервируют для контейнера
отдельные физические ядра или объём RAM.

## 4. Что происходит при первом запуске

Команда `docker compose up -d` читает `compose.yaml`. Compose подставляет
переменные из окружения и необязательного `.env`, получает отсутствующие
образы, создаёт сеть `local-ai_default`, два тома и два контейнера.
Ключ `-d` оставляет процессы работать в фоне.

Далее каждый сервер готовит свою модель:

1. `llm` получает из Hugging Face файлы
   `Qwen/Qwen2.5-7B-Instruct-GGUF`. Указан первый файл разбиения
   `qwen2.5-7b-instruct-q4_k_m-00001-of-00002.gguf`; загрузчик получает и
   вторую часть. Эти два файла составляют одну модель.
2. Файлы Qwen попадают в `/models`, то есть в том `local-ai_llm-data`.
   Переменная `LLAMA_CACHE=/models` направляет туда кэш загрузчика.
3. `tei` получает конфигурацию, токенизатор и веса `BAAI/bge-m3` указанной
   ревизии. В проверенном ARM64-образе использован ONNX backend: в логах
   зафиксирована загрузка `onnx/model.onnx` и `onnx/model.onnx_data`.
4. Файлы BGE-M3 сохраняются в `/data`, в том `local-ai_tei-data`.
5. Серверы загружают модели, подготавливают рабочую память и выполняют
   необходимую инициализацию. После готовности `/health` отвечает успешно.

Состояние `running` означает, что процесс контейнера работает. Во время
скачивания весов это ещё не означает готовность к инференсу. Поэтому тест
отдельно ждёт успешного ответа `/health` каждого сервера.

Последующие запуски используют файлы из томов. Перезагрузка в RAM и прогрев
могут потребоваться снова. Большие веса повторно скачивать не нужно, если
они сохранены и выбран тот же вариант модели. Текущие загрузчики могут
обращаться к Hugging Face за метаданными; запуск в полностью изолированной
сети отдельно не проверялся.

## 5. Адреса, порты и путь запроса

В Compose записано отображение `адрес_хоста:порт_хоста:порт_контейнера`.

| Сервис | С macOS | Внутри сети Compose | Что слушает процесс |
| --- | --- | --- | --- |
| `llm` | `http://127.0.0.1:8000` | `http://llm:8080` | `0.0.0.0:8080` в контейнере |
| `tei` | `http://127.0.0.1:8080` | `http://tei:80` | `0.0.0.0:80` в контейнере |

Для запроса к Qwen путь такой:

```text
Python в macOS → 127.0.0.1:8000 → проброс порта Docker → llm:8080
```

Число `8080` встречается дважды, но конфликта нет: порт TEI на Mac и порт
llama.cpp внутри другого сетевого пространства — разные точки подключения.

`localhost` всегда относится к тому окружению, где выполняется клиент.
Из контейнера `tei` обращение к `localhost:8080` не означает обращение к
Qwen. Для связи внутри сети Compose нужно использовать `llm:8080`.
Имена сервисов разрешает DNS Docker.
[Сетевое взаимодействие в Compose](https://docs.docker.com/compose/how-tos/networking/).

Публикация на `127.0.0.1` предназначена для доступа с самого компьютера.
Слушание `0.0.0.0` **внутри контейнера** позволяет Docker доставить запрос
серверу и само по себе не меняет адрес публикации на Mac. Аутентификация API
в стенде не настроена; `--cors-origins localhost` у llama.cpp задаёт правила
доступа из браузера и не заменяет аутентификацию.

## 6. Как Qwen генерирует ответ

### 6.1. Почему выбраны GGUF и Q4_K_M

Используется инструктивная модель Qwen2.5-7B-Instruct в официальном GGUF
репозитории Qwen. `Instruct` означает настройку модели на выполнение
инструкций и диалог. Обозначение `7B` относится к классу числа параметров,
а не к размеру контекста или числу токенов в ответе.

GGUF хранит веса и необходимые метаданные в формате, который читает
llama.cpp. Q4_K_M — вариант смешанной квантизации с преимущественно
4-битным представлением весов; разные тензоры могут храниться с разной
точностью. Такое представление уменьшает размер весов и потребность в
памяти ценой некоторой потери численной точности. Квантизация не делает
все вычисления сервера 4-битными.
[Карточка Qwen GGUF](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct-GGUF).

### 6.2. Шаги обработки

1. Клиент отправляет JSON в `POST /v1/chat/completions`. Поле `model`
   содержит настроенный alias `Qwen2.5-7B-Instruct`.
2. Сервер преобразует список сообщений и ролей в текст по шаблону диалога.
   Служебные обозначения ролей тоже участвуют в представлении входа.
3. Токенизатор преобразует вход в последовательность числовых идентификаторов.
4. На этапе обработки запроса, обычно называемом **prefill**, модель
   вычисляет представления входных токенов.
5. На этапе **decode** сервер последовательно получает распределение для
   следующего токена, выбирает токен и добавляет его к уже сформированной
   последовательности. Так появляется ответ.
6. Вычисленные ключи и значения attention могут использоваться повторно
   через **KV-кэш**. Он экономит повторные вычисления, но занимает память.
7. Генерация заканчивается по условию остановки или по лимиту. Идентификаторы
   токенов преобразуются в текст, сервер собирает JSON-ответ.

В тесте `temperature=0` уменьшает случайность выбора токенов,
`max_tokens=16` ограничивает длину продолжения, а `stream=false` означает
получение одного итогового JSON вместо последовательности фрагментов.
Низкая температура не гарантирует правильность произвольного ответа.
Основные возможности и параметры сервера описаны в
[документации llama.cpp](https://github.com/ggml-org/llama.cpp/tree/master/tools/server).

В контрольном запросе учтены 51 входной и 3 сгенерированных токена,
всего 54. Видимый ответ — `42`. Счётчик токенов не равен числу символов:
на него влияют токенизация и служебные элементы формата модели.

Контекст ограничен 2048 токенами на единственный слот. При подготовке
запроса нужно учитывать сообщения, историю, шаблон диалога и место под
генерируемый ответ. Длинный диалог не получает бесконечной памяти.
Клиент передаёт нужную историю через `messages`; файлы весов не являются
хранилищем пользовательских разговоров.

### 6.3. Что означает OpenAI-совместимый API

Сервер принимает привычную структуру `model`, `messages`, `temperature`
и возвращает `choices`, `message`, `usage`. Это совместимость формата
запросов и ответов для поддерживаемых методов. Вычисления выполняет локальная
Qwen, обращение к платному облачному сервису для этого запроса не требуется.

Проверяемый результат доступен как
`response["choices"][0]["message"]["content"]`. Успешное завершение в
данном тесте дополнительно подтверждает `finish_reason="stop"`.

## 7. Как BGE-M3 получает эмбеддинги

Для каждого входного текста TEI выполняет следующую обработку:

1. Проверяет форму запроса, число входов и длину токенизированных текстов.
2. Токенизирует текст и формирует необходимые входы модели.
3. Передаёт входы энкодеру BGE-M3, который вычисляет контекстные
   представления токенов.
4. Получает представление всего текста с настроенным `pooling=cls`:
   используется представление специального начального токена.
5. При `normalize=true` нормализует полученный вектор и возвращает его
   в JSON-массиве. Здесь размерность равна 1024.

`Pooling` — способ получить одно представление текста из представлений
его токенов. `cls` и усреднение всех токенов — разные способы агрегации;
в конфигурации явно выбран `cls`.

Вектор — это координаты в пространстве признаков. У отдельной координаты
обычно нет простой подписи вроде «процент кошки». Практический смысл
проявляется при сравнении векторов. В текущем стенде используются dense
эмбеддинги. Другие режимы BGE-M3, такие как sparse и ColBERT, не включены.
[Описание BGE-M3](https://huggingface.co/BAAI/bge-m3).

### 7.1. Нормализация и косинусное сходство

Для вектора `v` длина, или L2-норма, вычисляется так:

```text
||v|| = sqrt(v₁² + v₂² + ... + v₁₀₂₄²)
v_normalized = v / ||v||
```

После нормализации норма приблизительно равна 1. Для ненулевых векторов
`a` и `b` косинусное сходство равно:

```text
cosine(a, b) = sum(aᵢ × bᵢ) / (||a|| × ||b||)
```

Для нормализованных векторов достаточно скалярного произведения.
Чем ближе направления векторов, тем выше значение. Это не вероятность,
не процент правильности и не универсальная шкала качества ответа.
Полезный порог сходства зависит от данных и задачи.

В контрольном примере:

| Сравнение с «Кошка спит на диване.» | Cosine similarity |
| --- | ---: |
| `A cat is sleeping on the sofa.` | 0,782093 |
| `Вулкан извергает лаву и пепел.` | 0,374135 |
| Точная копия русского предложения | 1,000000 |

Таким образом, для выбранного примера перевод оказался ближе постороннего
текста. Проверка не доказывает одинаковую точность на всех языках и темах.

### 7.2. Два формата API для одной модели

`POST /embed` принимает `inputs` и возвращает массив векторов.
`POST /v1/embeddings` принимает `input` и возвращает объекты в `data`,
где находятся `index` и `embedding`. Это два интерфейса одного TEI-сервера;
они не требуют двух копий BGE-M3.

Тест проверяет оба интерфейса и сравнивает векторы одного и того же текста.
Близость выше 0,999 подтверждает их согласованность на контрольных входах.

## 8. Как настройки связаны с ресурсами

Значения ниже взяты из текущего `compose.yaml`, а не из настроек модели по
умолчанию. Полученный `/info` TEI подтвердил `model_dtype=float32`,
`pooling=cls`, `max_input_length=512` и версию сервера `1.9.4`.

| Настройка | Значение | Практический смысл |
| --- | --- | --- |
| Qwen `--ctx-size` | 2048 | Размер рабочего контекста |
| Qwen `--parallel` | 1 | Один слот генерации; сервер не настроен на массовое одновременное обслуживание |
| Qwen `--threads` | 4 | Число вычислительных CPU-потоков для генерации |
| Qwen `--batch-size` / `--ubatch-size` | 128 / 128 | Логический и физический пределы порции токенов при обработке; это не 128 пользователей |
| Qwen `--n-gpu-layers` | 0 | Слои не передаются на GPU |
| TEI `--dtype` | float32 | Тип чисел, объявленный и подтверждённый этим сервером |
| TEI `--max-batch-tokens` | 512 | Бюджет токенов вычислительного батча; сервер также ограничил один вход 512 токенами |
| TEI `--max-client-batch-size` | 8 | До восьми входных текстов в одном клиентском запросе |
| TEI `--max-batch-requests` | 8 | Ограничение числа элементов, объединяемых сервером в вычислительный батч |
| TEI `--max-concurrent-requests` | 8 | Ограничение одновременно принятых запросов; оно не обещает восемь одновременных проходов модели |
| TEI `--tokenization-workers` | 2 | Два работника для подготовки входных текстов; это не лимит потоков ONNX Runtime |

Батч — это порция данных, обрабатываемая совместно. Клиентский список текстов
и вычислительный батч сервера не обязаны совпадать: TEI планирует обработку
с учётом ограничений. Восемь текстов по 512 токенов не превращают бюджет
одного вычислительного батча в 4096 токенов.

BGE-M3 как модель поддерживает более длинные входы, но текущий стенд
настроен на 512 токенов для экономии ресурсов. `--auto-truncate` разрешает
обрезание слишком длинного входа. Тест использует короткие предложения и
явно передаёт `truncate=false`, чтобы неожиданный избыток длины стал ошибкой.
[Параметры TEI](https://huggingface.co/docs/text-embeddings-inference/en/cli_arguments).

Файлы модели на диске, занятая сервером RAM и доступная память Docker — три
разные величины. RAM нужна также для промежуточных результатов, буферов,
KV-кэша Qwen и самой программы. Увеличение контекста или батчей может повысить
расход памяти даже при неизменном размере весов.

## 9. Где сохраняются данные

| Что | Где | Сохраняется при пересоздании контейнера |
| --- | --- | --- |
| Конфигурация, тест, документация | Рабочий каталог Git и GitHub | Да |
| Скачанные файлы Qwen | Том `local-ai_llm-data`, подключённый как `/models` | Да |
| Скачанные файлы BGE-M3 | Том `local-ai_tei-data`, подключённый как `/data` | Да |
| Рабочие тензоры и KV-кэш | RAM процесса | Нет |
| Итог теста | `artifacts/test-report.json` в каталоге проекта | Да; следующий тест перезаписывает этот файл |
| Вывод серверов | Логи контейнеров Docker | Ограничен ротацией и жизненным циклом контейнера |

На macOS именованные тома размещены в хранилище Linux VM Docker Desktop.
`/models` и `/data` здесь обозначают пути **внутри контейнеров**, а не папки
в корне macOS. В GitHub отправлены текстовые файлы проекта и отчёт;
многогигабайтные веса остаются в Docker.

`docker compose down` удаляет контейнеры и сеть проекта, сохраняя названные
тома. Добавление `-v` удаляет и тома проекта: после этого веса придётся
получить заново. Такое поведение объясняет, почему хранение вынесено из
изменяемого слоя контейнера.
[Тома Docker](https://docs.docker.com/engine/storage/volumes/).

В проекте нет отдельной базы истории запросов. Скрипт сохраняет краткий
отчёт: контрольные тексты, ответ Qwen, метрики и длительности. Полные
1024-мерные векторы в отчёт не записываются.

## 10. Готовность, перезапуск и версии

Docker вызывает `/health` внутри каждого контейнера с интервалом 30 секунд
и таймаутом 10 секунд. `start_period=20m` даёт время на первоначальную
подготовку, в течение которого неудачные проверки ещё не увеличивают счётчик
ошибок запуска. Это не обязательная задержка на 20 минут: успешная проверка
может подтвердить готовность раньше. После периода запуска настроено
`retries=10` последовательных неудач до статуса `unhealthy`.

`restart: unless-stopped` позволяет Docker перезапустить завершившийся
контейнер, если он не был намеренно остановлен. Сам статус `unhealthy`
в обычном Docker Compose не заставляет живой процесс автоматически
перезапускаться. Логи ротируются с параметрами `max-size=10m`, `max-file=3`.
[Параметры сервисов Compose](https://docs.docker.com/reference/compose-file/services/).

SHA256 digest в поле `image` фиксирует содержимое образа даже при изменении
тега. Для BGE-M3 дополнительно закреплена ревизия весов:

```text
5617a9f61b028005a4858fdac845db406aefb181
```

Для Qwen указаны репозиторий и имя файла, но ревизия в команде загрузки
не закреплена. В кэше контрольного запуска записана ревизия:

```text
bb5d59e06d9551d752d08b292a50eb208b07ab1f
```

Это наблюдение о выполненном запуске, а не гарантия будущего скачивания
на чистой машине. При замене `TEI_IMAGE` на x86_64-вариант из `.env.example`
также используется тег без зафиксированного digest. Эти детали задают
границы воспроизводимости текущего решения.

## 11. Как устроен проверочный скрипт

После разделения структуры 2 октября 2026 года `TextTest.py` проверяет только
языковую модель, `EmbeddingsTest.py` — только эмбеддинги. Общие функции вынесены
в `api_utils.py`, а команда `python3 test_api.py` по-прежнему выполняет обе
проверки. Тест одной модели не требует доступности другого сервера.

Скрипты используют стандартную библиотеку Python: `urllib` для HTTP,
`json` для обмена данными, `math` для численных проверок, `argparse`
для параметров запуска и `pathlib` для записи отчёта.

| Функция | Назначение |
| --- | --- |
| `request()` в `api_utils.py` | Выполняет GET или POST; сообщает HTTP-ошибки, проблемы соединения и некорректный JSON |
| `wait_ready()` в `api_utils.py` | Повторяет запрос к `/health` до готовности или истечения лимита |
| `test_llm()` в `TextTest.py` | Проверяет наличие модели, отправляет вопрос и проверяет структуру и содержание ответа |
| `validate_vectors()` в `EmbeddingsTest.py` | Проверяет число и длину векторов, конечность чисел и норму |
| `cosine()` в `EmbeddingsTest.py` | Вычисляет косинусное сходство двух векторов |
| `test_embeddings()` в `EmbeddingsTest.py` | Проверяет модель TEI, смысловую близость, перевод и оба интерфейса эмбеддингов |
| `run_checks()` в `api_utils.py` | Выполняет выбранные проверки, печатает результат, записывает JSON и выбирает код завершения |
| `main()` в `test_api.py` | Передаёт общему исполнителю обе группы проверок |

Для Qwen тест ожидает один ответ `assistant`, результат `42`, завершение
`stop` и положительный счётчик сгенерированных токенов.

Для BGE-M3 отправляются пять текстов: русское предложение, его английский
перевод, постороннее предложение, копия первого и русское перефразирование.
Тест проверяет:

- пять векторов по 1024 конечных числовых значения;
- отклонение L2-нормы каждого вектора от 1 меньше 0,01;
- сходство одинаковых текстов выше 0,999;
- сходство перевода больше сходства постороннего текста хотя бы на 0,05;
- сходство русского перефразирования больше сходства постороннего текста хотя бы на 0,05;
- два результата `/v1/embeddings` с индексами `[0, 1]`;
- сходство результатов двух интерфейсов для тех же текстов выше 0,999.

По умолчанию ожидание готовности составляет до 1200 секунд **на каждый
сервис**, а таймаут обычного API-запроса — 300 секунд. Время инференса и
проверок добавляется к ожиданию; `--wait` не является общим таймаутом всего
скрипта. Ожидаемая ошибка одной группы фиксируется, после чего проверяется
вторая. Код завершения 0 означает успех обеих групп, 1 — наличие ошибки.

## 12. Как это связано с поиском по документам

Построенный стенд можно использовать как основу для RAG — генерации ответа
с опорой на найденные документы. Для этого потребуются дополнительные
компоненты: загрузка и разбиение документов, хранение векторов и текстовых
фрагментов, поиск ближайших векторов и приложение, координирующее запросы.

Сначала документы разбивают на фрагменты и вычисляют их эмбеддинги через
BGE-M3. В индекс сохраняют векторы вместе с исходными фрагментами и ссылками
на источник. Когда приходит вопрос, приложение получает его эмбеддинг,
находит похожие фрагменты и отправляет **тексты найденных фрагментов и вопрос**
в Qwen. Вектор из 1024 чисел служит для поиска и не подставляется в обычный
чат-запрос как готовое знание.

Такого связующего приложения в текущем репозитории нет. Эта последовательность
показана на [отдельной схеме расширения](architecture.md#6-возможное-расширение-поиск-по-документам).

## 13. Как продемонстрировать работу

Из корня проекта выполните:

```bash
docker compose up -d
docker compose ps
python3 TextTest.py
python3 EmbeddingsTest.py
```

Для контейнеров в состоянии `paused` выполните `docker compose unpause`.
Чтобы проверить обе модели одной командой, используйте `python3 test_api.py`.

Для объяснения результата достаточно открыть [общую схему](architecture.svg),
показать два независимых сервера и их порты, затем показать
[`test-report.json`](../artifacts/test-report.json): ответ Qwen, размерность
эмбеддингов и сравнение сходства. Примеры самостоятельных запросов `curl`
приведены в [README](../README.md#примеры-запросов).

Если API недоступен, `docker compose logs --tail 100 llm tei` помогает
отличить скачивание весов, ошибку загрузки и нехватку ресурсов. Для остановки
стенда с сохранением моделей используйте `docker compose down`.
